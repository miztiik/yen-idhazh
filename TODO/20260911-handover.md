# Handover: how to pick up the plan queue with no context

**Last Updated**: 2026-09-11

You are a fresh agent and you know nothing about this repository. This page is where you start. It is the queue-specific instruction; the durable rules it points at live in [`../docs/`](../docs/) and are not repeated here.

---

## Step 1. Run the queue reader before you start anything

```powershell
python backend/utilities/plan_status.py --in-flight
```

It reads every Status Reckoner under `TODO/`, and it answers three things at once: what has landed, what can start now, and what a previous agent left half-done. It exits non-zero when a table disagrees with the repository.

**Deal with what it finds under `IN FLIGHT` before you dispatch a single new row.** A worker that is killed mid-row never writes a report, never opens a pull request, and never clears the `IN-FLIGHT` it was given, so the queue looks idle while the box is not. What it leaves is a checkout with edits in it and a branch nobody proposed. The reader names each one and says `ADOPT` or `REMOVE`; decide per item, and only then pick a row. Starting a fresh row beside an abandoned one is how a row gets done twice and how two branches end up writing one file.

Then deal with `DRIFT`. Every finding is a row whose table disagrees with the trunk. Correct it by hand - the tool never edits a plan-doc, because a merged pull request can still be the wrong thing to write into a row, and only a person who read that pull request can say. Prove the merge before you write it in:

```powershell
gh pr view <n> --json state,mergeCommit
```

The other modes, when you want them:

```powershell
python backend/utilities/plan_status.py                 # the queue, every live row, and its drift
python backend/utilities/plan_status.py --ready         # the dispatch list on its own
python backend/utilities/plan_status.py --plan 23       # one plan
python backend/utilities/plan_status.py --all           # include plans whose rows have all settled
python backend/utilities/plan_status.py --no-gh         # git only, where gh is unavailable
```

## Step 3. Pick a row

**The dispatch list is the reader's `READY NOW` output.** It is computed from the Reckoners every time you run it, so it cannot go stale.

[`20260911-execution-order.md`](20260911-execution-order.md) is the reasoning behind the order, not the list. Its collision table (section 3), its critical path (section 2) and its verified cross-plan edges (section 4) are worth reading before you compose a wave. **Its section 1, "What can start today", is a snapshot of 2026-09-11 and was wrong the moment the first row merged** - use the reader instead.

Two things the reader does not know, which is why you still read the plan:

- **A row's `Files touched` list is the collision check.** Compose a wave by diffing those lists, never by trusting a sentence saying the rows are disjoint. The reader tells you a row is ready; it does not tell you two ready rows write the same file.
- **`Parallel N` comes from the plan's own section 0**, and it bounds how many workers WRITE at once. It does not bound what they RUN.

Measured 2026-09-11 with the reader: 18 plan-docs under `TODO/` carry a live row, 118 rows are live between them, and 34 can start now. The execution-order page covers 5 of those 18 plans. The other 13 are open and unscheduled, not closed - eleven of them are plans 12 to 22, a chain behind [`20260905-11-two-call-planner-plan.md`](20260905-11-two-call-planner-plan.md), and the last two are [`20260823-known-defects-plan.md`](20260823-known-defects-plan.md) and [`20260827-summarizer-fine-tuning-plan.md`](20260827-summarizer-fine-tuning-plan.md), which stand alone. [`20260907-growing-reads-window-plan.md`](20260907-growing-reads-window-plan.md) has no live row left at all, whatever the pointers elsewhere still say.

## Step 4. Dispatch it

One worker per row. One fresh worktree per worker, cut from `origin/main`, in the sibling container beside this repository - never in the shared checkout. A named branch per row. Fill the row's `Worktree` cell when you create it.

Before dispatching, run the two checks [`../docs/how-to/execute-a-plan.md`](../docs/how-to/execute-a-plan.md) requires: every symbol the row names has to exist in the tree, and the row's oracle has to FAIL against the base tree. An oracle that already passes is measuring something other than the row.

Where two rows from different plans are ready together, check the collision table in [`20260911-execution-order.md`](20260911-execution-order.md) section 3 first, and merge one before dispatching anything that shares a file with it. The workers are parallel; the merge is serial.

## Step 5. What a row's pull request has to carry

**The row's own Reckoner line, in the same pull request.** `Status` becomes `DONE #<pr>`, and `Worktree`, `PR` and `Subagent` are filled. One line of one table, the row's own, and nothing else in the Reckoner. The number is not known while the branch is being written, so use the `PR #_pending_` placeholder and the stamp commit in [`../docs/how-to/ship-a-pr.md`](../docs/how-to/ship-a-pr.md).

This is why the rule exists, and it is this queue's own history: pull request **#608** merged row `#P1` of [`20260910-23-article-classification-plan.md`](20260910-23-article-classification-plan.md) on 2026-09-11 and changed no Reckoner line. The row read `PENDING` with an empty `PR` column for the rest of that day, while the work was on the trunk. The instruction to flip it afterwards had been written down and was read by the agent that did not do it. Wording alone did not hold, so the update moved inside the diff that gets reviewed.

**A row that invalidates a number on [`20260911-execution-order.md`](20260911-execution-order.md) refreshes it, in the same pull request.** That page is derived, so it does not stay true on its own, and saying in a pull request that a page is stale is not updating it. Which sections go stale, and when:

| Section | What makes it stale |
| --- | --- |
| 0. The five plans and their counts | any row landing, or a plan gaining or losing a row |
| 1. What can start today | any row landing. The reader replaces this section; do not re-derive it by hand |
| 2. The critical path and the longest pole | a row landing on the path, or a `Depends-on` changing |
| 3. Where two plans write one file | a row widening or narrowing its `Files touched` list |
| 4. The cross-plan dependencies | a `Depends-on` cell changing in any of the five plans |
| 5. The shortest path to something a reader can see | a row on that path landing |
| 6. The documentation set | a plan adding or retiring a page |

If a row changes nothing on that page, say so in the pull request in one line. That is a different sentence from "this page is stale".

## Standing traps

These cost a run each. They are not negotiable and they are not ordered by importance.

- **Never touch the shared checkout.** Every code change happens in its own worktree on its own branch.
- **Stage explicit paths.** Never `git add .`, never `git add -A`. Verify with `git diff --cached --name-only` before committing.
- **Never force-push, `git stash`, `git reset --hard`, or `git clean -fd`.** One workflow force-pushes on a schedule and it is the only exception in the repository (`CLAUDE.md` section 8).
- **Commit, push and open the pull request BEFORE the heavy gates.** CI is six to fifteen times faster than this box and it is the authoritative arm.
- **Do not run the full pytest suite, the browser suite, or `ruff format` locally.** Run the checks for what you changed. `ruff format` is not a gate and running it rewrites files nobody asked you to touch.
- **Re-measure every number a plan hands you.** A plan-doc is written before the work and read after the tree moved under it. `CLAUDE.md` Rule #10: an unmeasured number may not justify a design.
- **`gh pr merge --squash --delete-branch` can exit 1 after succeeding.** It fails on the branch delete when a worktree still holds the branch, and the merge has already happened. Confirm with `gh pr view <n> --json state,mergedAt,mergeCommit`, never with the exit code.
- **Remove the row's worktree BEFORE the merge, and never by detaching it.** Detaching frees the branch and throws away the only signal a later sweep can judge the leftover on.
- **Write new text with LF before the first check.** Git normalises at `git add`, which is after a check has already read the working file.
- **A new backend test module needs a mark, or a line in `UNMARKED_MODULES` in `backend/tests/test_marks.py`.** The registered marks are `contract`, `visual`, `slow` and `workflow`; there is no `unit` mark.

## The standing guideline every plan's Operating Contract already states

Follow the INTENT, not the letter. Where a row's wording and its purpose disagree, the purpose wins - and say in your report which you followed and why.

Prefer a structural fix over a small diff. `CLAUDE.md` Rule #5 forbids the band-aid: if the right correction is a level higher than the row assumed, escalate the level rather than patching around it. A row that turns out to be wrong is a finding worth reporting, not an obstacle to route around quietly.

Turn every defect you find on the way into explicit work: fix it in the row if it is in scope, or write a follow-up row. Do not bury it in a footnote.

## Three gaps nothing on the queue owns

Each of these is real, none is assigned to a row, and none blocks a dispatch. They are here so the next agent does not rediscover them.

1. **The prompt loop goes unmonitored.** [`20260910-23-article-classification-plan.md`](20260910-23-article-classification-plan.md) row `#7b` folds the two model calls into one directed graph. `backend/utilities/prompt_loop.py` drives the summariser prompt against the incumbent through that boundary, and no row says what happens to it when the boundary moves. It is an offline maintenance tool that reaches no reader, so nothing in CI fails when it stops working.

2. **Four prunes are switched off.** `config/idhazh.json` has `retention.dry_run: true`. Every retention pass reports what it would delete and deletes nothing, so a row that adds a prune adds a no-op. Somebody has to decide when that flag flips, and the plans do not say who.

3. **Plan 23's budget rests on an estimate.** Its own row `#P4` is what would replace that estimate with a measurement on the runner, and `#P4` has not run. Every wall-clock figure in that plan is therefore an estimate under `CLAUDE.md` Rule #10 until it does, and Rule #10 says an estimate may not justify a design. Treat the plan's cost arithmetic as provisional and dispatch `#P4` early.
