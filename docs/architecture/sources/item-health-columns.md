# Item Health Columns

**Last Updated**: 2026-09-21

Where each of item health's 123 columns comes from: which module puts a value
under the name, whether that value reaches the ledger row, and whether any
committed row carries it. [item-health.md](item-health.md) is the ledger - what
it is for, where it lives, what a column means, what counts against a source.
This is one question about it, and the question a person arrives holding is
"who fills this cell, and does anything".

## The table is generated, and this is the command

```text
python backend/utilities/item_health_provenance.py
```

Paste its output over the block below, whole. A hundred and thirteen rows kept
by hand is a hundred and thirteen rows that drift, and this page exists because
three partial lists of these columns had already drifted apart from each other.

**The utility is an operator script and not a test, deliberately.** It reads
every day file of `state/item-health/` to answer the last column, which is a
read whose cost grows with the archive (`CLAUDE.md` Guardrail #12) and which
section 13 forbids a test to do. It also refuses to print anything at all when
the eight groups stop covering `ItemHealthRow.csv_columns()` exactly, so a
column minted with no group fails the run rather than going missing from the
table.

## What "computed in" means, and what it cannot tell you

A module is named when it puts a value **under that name on its way into this
row**. Four shapes do that: a keyword of the `ItemHealthRow(...)` construction,
a keyword of the per-item record the work stage emits while it runs, a key of a
dict whose every key is a column of this row, and a class whose every field is
one. Using the same word for something else is not producing a cell - `date` is
a column on nine other contracts and `tier` is a property of a source - and the
first scan, which counted every use of the word, named 37 modules for `date`
and said nothing.

The contract that declares the row is the one module left out by name. It holds
all 119 fields by construction and fills none of them: a contract says what a
cell may be, never what it is.

**A dash under `Computed in` means nothing in `backend/idhazh/` puts a value
under that name.** No column carries one. The last three did until 2026-09-16 -
the model server's own prefix-cache state, which nothing had asked it for.

**`Reaches the row` is the column the rest of this page is for.** A cell that
is computed on every item and named in no row is measured and thrown away: it
reaches a log line that the CI run keeps for two days, and the ledger - the only
durable record - never sees it. That is the difference between a column nobody
measures and a column nobody carries, and the two look identical in the file.

**A dash there beside a `yes` in the archive is the recorder's path, not a
contradiction.** The scan attributes a cell to a module that names it in an
`ItemHealthRow(...)` construction; the work stage instead hands its cells to
`telemetry.record.ItemRecorder`, which builds the row out of a mapping no static
read can attribute one name at a time. So every machine cell reads as a dash
here and lands on every row a shard sealed. `census.py` is the only module the
scan can credit, because it is the only one that spells the keywords.

Two things it cannot settle. Whether the module it names is the **right** place
to compute a column: it says one module binds the name, never that one should.
And whether a filled column is filled **correctly** - what a cell's value ought
to be is the contract's business and the producer's, not this page's.

## An empty column means nothing carries it yet

**Read an absence as "nothing carries this into the row", never as "this item
had no value".** For most of this page's life that was the whole story: 70 of
113 columns were empty because each had landed with the instrument that measures
it and without the wiring that carries the same value into the ledger row.

**That is over.** Since 2026-09-16 both writers prefer the row the shard sealed
rather than rebuilding it from the article and the summary payloads. The first
day published under that rule filled **66 columns at once**: 43 of 113 over the
23 days before it, 109 of 113 with it. Nine are still empty, and each one is
empty for a reason of its own rather than for want of wiring:

| Column | Why nothing carries it |
| --- | --- |
| `truncation_cap_tokens` | The cap has never fired on a committed day. A cell nothing cut is empty, not zero |
| `cgroup_peak_bytes` | The kernel file is absent on every GitHub-hosted runner this project has probed |
| `failed_field` | No refused reply has yet named one field. It fills the day a reply is refused for a reason that has one |
| the six `os_` columns | Minted 2026-09-17. No run has written a row yet |

**The six `os_` columns are the machine's own account of itself**, against the
RSS marks above them, which are what a process held. They are also the only
reading that can say whether these runners carry swap at all: nothing committed
records it today, so the first day written after they land is the measurement.

That count is a reading and not a rule (Guardrail #10). Re-run the command
rather than trusting this paragraph.

**Every column has a producer.** `slot_id`, `kv_tokens_at_start` and
`prefix_shared_with_previous` were the last three with none, because nobody had
asked the model server whether it reports its prefix-cache state. It does, on
the reply the summarizer already reads, and since 2026-09-16 the row carries all
three off the item's first model call -
[../summarize/model-boundary.md](../summarize/model-boundary.md#the-outward-shim)
owns what each one means and why the second call is excluded.
